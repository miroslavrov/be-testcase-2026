# AgentHub — техническое задание

---

## Контекст

**AgentHub** — платформа для запуска AI агентов в B2B-сегменте. Компании подписываются на план, получают пул вычислительных слотов и отправляют задачи на исполнение.

Во время выполнения агент последовательно вызывает **инструменты (tools)**: читает данные, отправляет сообщения, запускает деплои. Часть инструментов требует явного подтверждения человеком — выполнение агента приостанавливается и ждёт решения согласующего.

**Важно:** агенты и инструменты в этом задании — моки. Агент — воркер, который итерирует по заранее заданному списку tool calls. Инструмент — `sleep(N ms)` + случайный успех/ошибка. 

---

## Домен

### Ключевые сущности

**Organization** — Все данные изолированы по организации.

**Plan** — тарифный план, определяет:
- максимальное количество одновременно занятых слотов
- месячный бюджет в USD

**Subscription** — активная подписка организации на план.

**AgentSlot** — вычислительный ресурс. Имеет тип (`standard` / `fast`) и статус. Слот может быть занят только одной задачей одновременно.

**Task** — единица работы. Содержит упорядоченный список tool calls, которые агент должен выполнить последовательно.

**TaskExecution** — конкретный запуск задачи на слоте.

**ToolDefinition** — описание инструмента: название, уровень риска (`read` / `write` / `destructive`), базовая стоимость вызова, параметры мока.

**ToolCall** — один вызов инструмента в рамках TaskExecution: входные параметры, статус, результат, стоимость.

**ApprovalChain** — настроенная для организации цепочка согласования: список шагов с ролями согласующих и таймаутами.

**ApprovalRequest** — запрос на согласование конкретного ToolCall. Создаётся, когда уровень риска или стоимость инструмента превышает порог автосогласования.

**User** — член организации с ролью (`owner` / `admin` / `approver` / `member`).

## Жизненный цикл задачи

```
submitted → queued → running → completed
                             ↘ failed

Внутри running — для каждого tool call:
  → auto_approved → executing → completed
  → awaiting_approval → [решение человека] → executing → completed
                                           ↘ rejected → task: failed
```

При создании задачи платформа проверяет лимиты подписки. При запуске — резервирует слот. Во время исполнения для каждого tool call определяет, нужно ли согласование. Если да — приостанавливает выполнение и ждёт решения.

**Статусы задачи:** `submitted` → `queued` → `running` / `awaiting_approval` → `completed` / `failed` / `cancelled`

**Статусы tool call:** `pending` → `awaiting_approval` / `executing` → `completed` / `failed` / `rejected`

## API

Базовый путь: `/v1`. Аутентификация: JWT Bearer.

### Аутентификация
```
POST /v1/auth/token      — получить токены
POST /v1/auth/refresh    — обновить access token
```

### Задачи
```
POST   /v1/tasks              — создать задачу
GET    /v1/tasks              — список (фильтр по статусу, пагинация)
GET    /v1/tasks/{id}         — детали + текущий tool call + статус approval
POST   /v1/tasks/{id}/cancel  — отменить
```

Пример тела при создании:
```json
{
  "title": "Analyze Q3 reports",
  "required_slot_type": "standard",
  "priority": 3,
  "tool_calls": [
    { "tool_name": "read_database", "input_params": {}, "estimated_cost_usd": 0.01 },
    { "tool_name": "send_email",    "input_params": {}, "estimated_cost_usd": 0.50 },
    { "tool_name": "deploy_service","input_params": {}, "estimated_cost_usd": 8.00 }
  ]
}
```

### Согласования
```
GET    /v1/approvals       — список ожидающих решения (только для роли approver)
GET    /v1/approvals/{id}  — детали: tool call, входные параметры, история шагов
POST   /v1/approvals/{id}/approve
POST   /v1/approvals/{id}/reject
```

### Подписка и биллинг
```
GET  /v1/subscription              — текущий план, использование бюджета
GET  /v1/invoices                  — история инвойсов
GET  /v1/invoices/{id}
```

## Бизнес-правила

### Лимиты при отправке задачи

Перед постановкой в очередь проверяются два условия:
1. Сумма фактически использованного бюджета за текущий период плюс `estimated_cost` задачи не превышает `plan.monthly_budget_usd`
2. Подписка организации активна

Если условия не выполнены — задача отклоняется с соответствующей ошибкой.

### Согласование tool call

Перед выполнением каждого tool call воркер определяет, требуется ли согласование:
- Если `tool.risk_level = 'read'` — всегда автосогласование
- Если `tool_call.estimated_cost_usd < plan.auto_approve_threshold_usd` — автосогласование
- Иначе — создаётся `ApprovalRequest` по цепочке организации для данного уровня риска

Пока ApprovalRequest открыт, задача находится в статусе `awaiting_approval`. Воркер не продолжает выполнение.

### Цепочка согласования

Каждый шаг цепочки имеет:
- роль согласующего
- таймаут (в часах)
- действие при истечении таймаута: перейти на следующий шаг или автоотклонить

При `approve` на последнем шаге — tool call переходит к исполнению.  
При `reject` на любом шаге — tool call отклонён, задача переходит в `failed`.

### Биллинг

После завершения каждого tool call создаётся запись об использовании с фактической стоимостью.

Раз в период (симулируется отправкой запроса) генерируется инвойс на основе накопленных записей.  
Один инвойс — один период — одна организация. Повторный запуск генерации не должен создавать дубли.

## Требования к реализации

### Многоинстансность

Все компоненты (API, воркеры) могут запускаться в нескольких экземплярах одновременно. Корректность системы не должна зависеть от того, сколько инстансов работает.

Несколько ситуаций, которые стоит проработать:

**Два воркера видят один свободный слот.** Оба пытаются зарезервировать его под разные задачи. Что происходит?

**Два инстанса API одновременно получают задачи от одного тенанта у предела бюджета.** Каждый по отдельности видит достаточный остаток. Оба ставят задачи в очередь. Что происходит с бюджетом?

**Биллинг-джоб запускается на двух инстансах с разницей в несколько секунд.** Оба начинают генерировать инвойс за один период. Что происходит?

**Воркер упал в момент исполнения task.** Слот помечен как занятый. Задача застряла в статусе `running` навсегда.

Клиенты могут повторять запросы при сетевых сбоях. `POST /v1/tasks` принимает заголовок `Idempotency-Key`. Повторный запрос с тем же ключом должен вернуть тот же результат без создания дублей.

## Тесты

### Обязательные

**Конкурентное резервирование:**  
50 параллельных воркеров пытаются захватить слоты из пула в 10 единиц.  
Ожидаемый результат: ровно 10 успешных резерваций. Ни одного дубля.

**Idempotency key:**  
Один и тот же POST /v1/tasks с одинаковым `Idempotency-Key` выполнен 3 раза.  
Ожидаемый результат: одна задача в БД, все три ответа содержат один и тот же `id`.

**Биллинг без дублей:**  
Функция генерации инвойса вызвана дважды параллельно для одной организации.  
Ожидаемый результат: один инвойс в БД.

### Интеграционный сценарий

```
1. Создать организацию, подписать на план (auto_approve_threshold = $1.00)
2. Добавить 2 слота типа 'standard'
3. Настроить approval chain: write → approver (таймаут 1 мин)
4. Создать задачу: [read_db($0.01), send_email($0.50), deploy_service($5.00)]

5. Проверить: read_db выполнился автоматически (ниже порога, risk=read)
6. Проверить: send_email ждёт решения (выше порога)
7. Согласовать → send_email выполнился
8. Проверить: deploy_service ждёт решения
9. Отклонить → задача перешла в failed
10. Проверить: usage_records созданы для завершённых tool calls
11. Проверить: state_transitions отражают полный путь
```

1. **Исходный код** в git-репозитории (форк текущего)
2. **README.md** — как запустить локально, как запустить тесты
3. **Миграции** — SQL или migration-файлы в порядке применения
4. **ADR.md** (1 страница) — ответы на вопросы:
   - Как обеспечена корректность при параллельном резервировании слотов?
   - Как воркер узнаёт о решении согласующего?
   - Как предотвращено дублирование инвойсов при нескольких инстансах?
   - Какие компромиссы вы сознательно приняли из-за ограниченного времени?

5. Презентация для демонстрации (в формате хакатона)

## Критерии оценки

| Область | На что смотрим |
|---|---|
| Корректность при конкурентном доступе | Слоты, бюджет, инвойсы — нет дублей и гонок |
| Схема БД | Инварианты, индексы, аудит |
| API | Семантика, обработка ошибок, idempotency |
| Тесты | Конкурентный тест, e2e сценарий |
| ADR | Понимание компромиссов, не только «как», но и «почему» |

## Что не нужно реализовывать

- Реальный AI / LLM
- Реальную отправку уведомлений (достаточно записи в таблицу)
- Реальный процессинг платежей
- Фронтенд

- Возможно частичное выполнение задания, в случаях если невозможна реализация отдельных требований/функций. В таком случае, в отчете важно подсветить аспекты, которые не были реализованы
