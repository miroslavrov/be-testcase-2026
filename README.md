# AgentHub

Бэкенд платформы запуска AI-агентов: задачи из tool call'ов, пул слотов, согласование дорогих вызовов человеком, биллинг. Тестовое задание, само ТЗ лежит в [TASK.md](TASK.md).

Стек: Go 1.26 (роутинг на стандартном net/http), PostgreSQL 16, pgx, goose для миграций. Очередь, лизы и все гонки решаются средствами постгреса, брокеров нет.

## Как запустить локально

Через docker compose (поднимет постгрес, применит миграции, запустит api и воркер):

```bash
make up
docker compose run --rm api seed
```

Сид создаёт демо-оргу Acme Corp: план на 10 слотов и $100 бюджета в месяц, порог автосогласования $1, три слота, четыре инструмента и две цепочки согласования (write: approver; destructive: approver, потом owner). Пароль у всех пользователей `password123`:

| email | роль |
|---|---|
| owner@acme.test | owner |
| admin@acme.test | admin |
| approver@acme.test | approver |
| member@acme.test | member |

API слушает на http://localhost:8080, живость проверяется через `GET /health`.

Можно и без докера, нужен только свой постгрес:

```bash
export DATABASE_URL=postgres://agenthub:agenthub@localhost:5432/agenthub?sslmode=disable
make migrate
make seed
go run ./cmd/api      # в одном терминале
go run ./cmd/worker   # в другом, инстансов может быть сколько угодно
```

Переменные окружения (у всех есть дефолты, пример в `.env.example`):

| переменная | дефолт | что делает |
|---|---|---|
| HTTP_ADDR | :8080 | адрес api |
| DATABASE_URL | postgres://agenthub:agenthub@localhost:5432/agenthub?sslmode=disable | строка подключения |
| JWT_SECRET | dev-secret-change-me | секрет подписи токенов |
| WORKER_CONCURRENCY | 2 | горутин-исполнителей в одном процессе воркера |
| DB_MAX_CONNS | 16 | размер пула коннектов |

## Потыкать руками

Получаем токен:

```bash
curl -s localhost:8080/v1/auth/token \
  -d '{"email":"member@acme.test","password":"password123"}'
```

Из ответа берём `access_token` и создаём задачу. Заголовок `Idempotency-Key` не обязателен, но с ним повторный запрос при сетевом ретрае вернёт ту же задачу вместо дубля:

```bash
curl -s localhost:8080/v1/tasks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: demo-1" \
  -d '{
    "title": "Analyze Q3 reports",
    "required_slot_type": "standard",
    "priority": 3,
    "tool_calls": [
      {"tool_name": "read_database",  "input_params": {}, "estimated_cost_usd": 0.01},
      {"tool_name": "deploy_service", "input_params": {}, "estimated_cost_usd": 5.00}
    ]
  }'
```

`read_database` дешёвый и с риском read, воркер выполнит его сам. `deploy_service` за $5 и destructive, поэтому задача встанет в `awaiting_approval`. Дальше под approver'ом:

```bash
curl -s localhost:8080/v1/approvals -H "Authorization: Bearer $APPROVER_TOKEN"
curl -s -X POST localhost:8080/v1/approvals/{id}/approve \
  -H "Authorization: Bearer $APPROVER_TOKEN" -d '{"comment":"ok"}'
```

Цепочка для destructive двухшаговая, так что после approver'а то же самое должен нажать owner. После этого воркер доисполнит задачу, `GET /v1/tasks/{id}` покажет статусы вызовов, текущий вызов и историю решений.

Инвойс за период генерируется запросом, это симуляция периодической джобы из ТЗ:

```bash
curl -s -X POST localhost:8080/v1/invoices/generate \
  -H "Authorization: Bearer $OWNER_TOKEN" -d '{"period":"2026-08"}'
```

Повторный вызов вернёт тот же инвойс, дублей не будет. Список эндпоинтов совпадает с ТЗ, сверх него только `POST /v1/invoices/generate` и `GET /health`.

## Как запустить тесты

Тестам нужен постгрес с применёнными миграциями, подойдёт тот же из compose:

```bash
make up      # если база ещё не поднята
make test
```

Тесты берут строку подключения из `TEST_DATABASE_URL`, потом из `DATABASE_URL`, потом дефолтный localhost. Если базы нет, интеграционные тесты скипаются, а юнитовые (auth, мок инструментов) проходят и без неё.

С race-детектором (нужен установленный gcc, включается cgo):

```bash
make test-race
```

Где лежат обязательные тесты из ТЗ:

- конкурентное резервирование, 50 воркеров на пул из 10 слотов: `internal/worker/reserve_test.go`. Ровно 10 успешных, все слоты разные, проигравшие получают ErrNoFreeSlot
- идемпотентность создания задачи: `internal/tasks/idempotency_test.go`. Три параллельных запроса с одним ключом, в базе одна задача, все ответы с одним id
- инвойс без дублей: `internal/billing/invoice_test.go`. Две параллельные генерации за один период, в базе один инвойс
- сквозной сценарий из ТЗ: `internal/integration/scenario_test.go`. read автоматом, send_email после approve, deploy_service отклонён, задача failed, usage_records по двум завершённым вызовам, журнал переходов отражает полный путь

## Как это устроено внутри

Коротко, подробности и почему именно так — в [ADR.md](ADR.md).

Воркер забирает задачу из очереди запросом с `for update skip locked`, в той же транзакции резервирует слот и заводит исполнение с лизом на две минуты. Лиз продлевается на каждом шаге. Если воркер умер, лиз протухает и исполнение подбирает любой другой инстанс: завершённые вызовы он распознаёт по статусу и просто шагает дальше, повторного списания денег не случится из-за уникальности usage_records по tool_call_id.

Перед каждым вызовом воркер решает, нужно ли согласование: read всегда автоматом, дешевле порога плана автоматом, иначе создаётся запрос по цепочке орги и задача паркуется в `awaiting_approval`. Слот при этом остаётся занят. Approve последнего шага возвращает исполнение в running с уже протухшим лизом, и его подхватывает первый свободный воркер. Reject сразу валит задачу и освобождает слот. Просроченные шаги досматривает свипер: эскалирует на следующий шаг или автоотклоняет, смотря что настроено в цепочке.

Каждый переход состояния задачи, исполнения и вызова пишется в `state_transitions`: кто, когда, из какого статуса в какой. Уведомления согласующим складываются в таблицу `notifications`, реальной отправки по ТЗ не нужно.

## Отступления от ТЗ и что не сделано

- в сценарии ТЗ порог автосогласования $1.00, но send_email за $0.50 при таком пороге прошёл бы автоматом, а по сценарию должен ждать решения. В интеграционном тесте порог 0.10, чтобы шаги 6-7 реально случились. Считаю это опечаткой в ТЗ
- `GET /v1/approvals` в ТЗ помечен «только для роли approver», но шаги цепочки бывают и с ролью owner или admin (в сиде так). Поэтому смотреть согласования могут все три роли, а кто вправе решать на конкретном шаге, определяет роль этого шага
- проверка бюджета чуть строже буквы ТЗ: к фактическому расходу за период прибавляются оценки ещё не завершённых задач. Без этого можно было бы бесконечно ставить задачи в очередь, пока фактический расход не догнал лимит
- если под уровень риска у орги нет цепочки, вызов исполняется без согласования. ТЗ этот случай не описывает, оставил мягкое поведение: цепочка — настройка орги, её отсутствие не должно вешать задачи навсегда
- отмена задачи не прерывает уже начатый tool call мгновенно: воркер заметит отмену на границе шага и молча выкинет результат
- refresh-токены stateless, отзыва нет; пагинация простая, limit и offset; ручки для чтения notifications нет, они видны только в базе

## Структура

```
cmd/            api, worker, migrate, seed
internal/
  api/          роутинг, хендлеры, auth middleware
  tasks/        создание с идемпотентностью и бюджетом, список, отмена
  worker/       очередь, слоты, лизы, исполнение, мок инструментов
  approvals/    цепочки, approve/reject, свип таймаутов
  billing/      usage, инвойсы, подписка
  auth/         jwt, bcrypt
  audit/        журнал переходов состояний
migrations/     sql, применяются goose'ом по порядку
```
